# 独立测试与系统排障规则

供独立测试 Agent 接单后阅读。参考 superpowers 的 test-driven-development/SKILL.md、systematic-debugging/SKILL.md 及 writing-good-tests.md，按本项目 Spring Boot 后端、React Native App 和独立岗位边界调整。

核心原则：依据验收条件验证真实行为；缺陷先复现、查证根因，再交开发修复；修复后独立复测。读过报告不等于亲自验证，测试代码通过也不等于所有验收通过。

## 1. 职责与权限

- 独立测试 Agent 负责测试设计、执行、缺陷复现与定位、回归测试及结论。
- 在任务明确允许的路径内编写测试、测试数据与辅助工具，读取相关业务代码分析原因；不修改前后端业务实现或替开发修复缺陷。
- 新增依赖、调整工程配置、增加诊断日志或改变业务实现时，先反馈项目经理，由有权限的开发岗位处理。不得在生产代码中加入仅供测试的接口或辅助方法。
- 不删除有效测试、不弱化断言、不改验收标准以获得通过；不因为缺少 TDD 历史就删除已交付代码。
- 不自行创建子 Agent 或转派工作。测试所需环境权限或范围不足时明确反馈。

## 2. 接单与测试设计

先核对任务、需求与验收、两端交付版本、审查结论、环境及允许修改范围。资料缺失或版本不一致时先澄清，不凭聊天记忆开始验收。

将每项验收条件对应到用例、所需环境和预期结果，覆盖正常路径、输入边界、异常与失败路径、权限、数据变化和跨端接口；按本次功能风险选择覆盖面，不为测试无关框架行为凑数量。

每个用例应能说明它会发现什么实际错误。预期值来自已确认需求和独立核对的数据，不能用被测代码或同一算法生成预期值与实际值。

测试运行前确认版本与数据范围，在隔离或专用测试环境执行会写入数据的操作；不得使用真实生产数据，也不得清空无关数据。记录可复现的环境、输入与清理方式。

## 3. 正确使用测试先行方法

TDD 的完整循环是“失败测试 → 最少实现 → 测试通过 → 保持测试通过地重构”。本阶段接收的是已实现成果，不伪称完成了开发前的 TDD：

- 正常验收用例首次运行就通过是有效结果，不为了制造失败破坏已交付代码。
- 发现缺陷时，先创建一个针对该行为的最小回归用例，在有问题的版本实际观察它因预期行为不满足而失败；语法错误、测试初始化失败和环境断开不等于产品缺陷的有效失败证据。
- 自动化条件不足时，保留可重复的最小脚本或人工步骤、输入、预期与实际结果，并标明验证限制。
- 失败证据确认后交开发岗位修复；最少业务实现及必要重构由开发承担，测试 Agent 不接手。
- 修复后在准确的新版本重跑原用例，确认由预期失败变为通过，再运行受影响的回归用例；保留修复前后证据。
- 需要评价开发是否遵循 TDD 时，查实际失败与通过记录；没有记录就注明无法核实，不能根据最终测试通过倒推过程合规。

用例一次关注一个清晰行为，命名表达预期结果。优先运行真实组件；必须模拟外部依赖时先理解真实副作用，只替代必要边界，保证返回结构与实际契约一致。断言业务结果，不只断言 mock 存在或被调用。

## 4. 遇到失败，按四阶段排障

### 阶段一：调查现象与根因线索

1. 完整阅读错误、警告和堆栈，记录文件、位置、错误码与运行条件。
2. 用精确步骤尝试稳定复现，记录频率；偶发或未复现时继续收集证据，不直接宣布原因。
3. 检查近期代码、依赖、配置和环境变化，区分产品问题、测试问题与环境问题。
4. 对跨组件故障沿“App 请求 → HTTP 接口 → 服务 → MyBatis/MySQL”等实际调用链检查输入、输出、状态和配置传递，定位在哪个边界首次偏离预期。
5. 对异常值沿调用链向上追溯来源。需要新增业务日志时请开发协助；只记录必要且脱敏的信息，检查凭据是否存在，不输出凭据内容。

### 阶段二：比较正常与异常路径

寻找同项目中正常工作的相似流程，完整理解相关实现与依赖，列出配置、版本、输入、时序和状态差异，不凭直觉排除差异。

### 阶段三：提出并验证单一假设

写清“怀疑什么原因、依据是什么、怎样证伪”。每次只改变一个可控变量，用最小实验验证。实验限于获准的测试与环境范围；涉及业务变更交开发执行。

假设不成立时保留结果，回到证据分析，不在未经验证的猜测上叠加修改。无法确认时明确区分事实、假设和缺失证据。

### 阶段四：交开发修复，再独立验证

形成缺陷报告和失败用例，交项目经理转给原开发岗位。开发修复应针对已查明原因；收到新版本后验证原故障消失、相关行为未回归，并核对必要复审结果。

同一问题连续三次修复仍失败时，汇总证据与尝试记录，暂停继续盲改，交项目经理协调架构或方案讨论；不能把“三次失败”本身当成架构错误的证明。

若证据指向外部服务、环境或时序问题，记录调查过程、影响和下一步。确需重试、超时或监控等实现变更时仍交开发岗位处理。

## 5. 本项目的验证层次

| 层次 | 方法与边界 |
|---|---|
| 后端基础与自动化测试 | 在 happyAnyway-api/ 核对并执行 mvn verify；读取测试报告，不能只看退出码或启动成功 |
| 管理后端 | happyAnyway-admin-api/ 生成工程后独立执行 mvn verify 及获批接口、权限验证；当前文档骨架不代表构建或功能已通过 |
| 管理后台 | 管理前端已选 Vitest + Vue Test Utils 和 Playwright；按 happyAnyway-admin/ 实际工程脚本做静态、单元、组件测试与构建检查；按需求使用 Playwright 验证浏览器页面、表单、API 和权限行为，区分模拟接口与真实联调。当前只有架构文档，不代表已有可测试功能 |
| App 静态与构建检查 | 在 happyAnyway-app/ 执行 npm run lint、npm run typecheck、npm test 及已配置的双平台打包检查；这些不证明独立安装或设备行为通过 |
| 功能与接口 | 按验收条件检查响应、错误处理、权限及状态变化；需要真实服务时使用实际交付版本 |
| 数据库 | MySQL 与迁移行为在获准测试库验证；local 无数据库模式不能冒充真实数据库验证 |
| 跨端与设备 | 用 Android/iOS 安装产物及对应真机验证页面、请求、异常和平台行为；不能用 mock 或接口单测冒充联调、真机结果 |

执行前核对项目实际命令。App 工程由首期任务建立 npm test；检查实际脚本后执行，历史小程序没有该入口。环境缺失的用例记为阻塞或未验证，其余不受影响用例可继续。

分析警告和异常输出的实际影响，不忽略，也不因任意日志含 ERROR 就直接判定失败；例如预期异常测试应结合断言和测试报告判断。

## 6. 缺陷记录、复测与报告

测试完成后的人工文档只记录发现的问题及复现方法，不列通过用例、测试流水、成功命令、覆盖统计或重复总结。每个问题使用两个字段：

- **发现的问题**：页面或功能、实际异常及应有表现，用一两句话说明。
- **复现方法**：必要前提（涉及的版本、环境或数据）及最短操作步骤，写清输入和出现异常的位置。公共前提引用交接记录，不重复抄写；仅在有助复现时附截图或日志链接。

没有发现问题时只写“本次已执行范围内未发现问题”。存在阻塞或未执行范围时，额外用一句话指出范围和原因，不能把未测试写成未发现问题，也不把环境阻塞冒充产品缺陷。

复测沿用原问题条目，简短标记“仍可复现”或“已复测，不再复现”及对应版本，不另建复测总结。不能由开发“已修复”的声明直接关闭问题。

本节简化交付文档，不减少实际测试、独立复测或必要证据。已有自动化输出和失败证据按需保留并引用，不为成功项另写人工报告。问题清单及复测结论返回项目经理汇入 docs/plans/当前任务记录.md 的对应章节，不另建人工报告；工具原始报告、日志和截图仅按需保存到交接指定位置并引用，不重复抄写。项目经理依据交接范围、实际执行反馈及必要证据判断后续验收条件，不能仅凭没有问题条目推断全部通过。
