# Agent 初始化与创建

供项目经理使用。用户说“初始化 agent”“创建其他 agent”或同义指令时，立即按本文件执行，不停在介绍流程或再次询问是否创建。

本指令授权初始化下表中已有配置的独立持久化岗位；不授权业务开发、改写岗位职责、创建子 Agent 或自动提交、推送、发布。用户指定某个岗位时只处理该岗位。

## 1. 默认初始化清单

按以下顺序逐个创建或复用，并核验接手结果：

| 岗位 | 配置（相对项目根目录） | 建议任务名称 |
|---|---|---|
| 后端开发 | happyAnyway-api/agent.md | happyAnyway 后端开发 Agent |
| 管理后端开发 | happyAnyway-admin-api/agent.md | happyAnyway 管理后端开发 Agent |
| App 开发 | happyAnyway-app/agent.md | happyAnyway App 开发 Agent |
| 管理后台开发 | happyAnyway-admin/agent.md | happyAnyway 管理后台开发 Agent |
| 独立测试 | tests/agent.md | happyAnyway 独立测试 Agent |

根 Agent 已是项目经理，不另建项目经理或产品 Agent。审查由项目经理在第五步按[审查规则](rules/code-review.md)按需创建子 Agent，不属于持久化岗位初始化清单，也不作为缺岗报告。新增岗位先由用户确定配置，再加入清单。

## 2. 读取配置，查询实际岗位

1. 以本文件所属项目为准确定根目录，不能误用当前会话的旧项目目录。读取根 AGENTS.md、目标岗位配置及其必须阅读的资料，核实版本来源与当前文件状态。
2. 如有 docs/agent-roster.md，先读取现有岗位登记；随后使用 list_threads、read_thread 核对实际任务，必要时按已知绑定查询归档任务。
3. 核实项目、岗位、独立任务类型、实际目录与未完成工作，不能只凭标题或 UUID 认定匹配，也不能仅凭登记为空认定缺岗。
4. 有符合职责的持久化实例就复用，不重复创建。已接手且配置未变时直接核实待命状态；配置变化需重新读取确认。忙碌岗位保留原工作，报告忙碌，不插入会中断原任务的初始化消息。
5. 无法判断重复实例或项目归属时，先补充查询；确实需要用户选择时只询问该歧义，其余明确岗位继续。

## 3. 创建缺少的持久化任务

使用 create_thread 创建独立任务，禁止使用 spawn_agent 或其他子智能体工具替代。

1. 先调用 list_projects，核对目标项目的实际路径和 Git 状态，取得正确 projectId。没有对应项目时报告需要添加项目，不在另一个项目中创建冒充成功。
2. 按工具要求选择环境：Git 项目默认 worktree，非 Git 项目使用 local；用户明确要求使用已保存项目时遵从。岗位默认模型与推理设置沿用用户配置，不自行覆盖。
3. 新任务的材料来源必须可访问：把本项目配置的实际绝对路径写进消息；有未提交资料或工作副本差异时交代来源，不假定副本已同步。这里只要求只读接手，实际开发工作区按第三步隔离规则另行核实。
4. 调用前在 docs/agent-roster.md 记录岗位、配置、创建方式、系统时间及完整拟发送消息，状态为待创建；文件不存在时按需创建。
5. 创建调用成功后保存返回的正式 threadId、hostId 和实际目录。只返回 clientThreadId 时标记创建中，等待正式 ID，不能提前标记就绪。调用失败记录失败，结果不确定先核实，不能盲目重建。

消息使用以下结构，发送前替换全部占位内容：

~~~text
你是本项目的<岗位>，作为独立持久化 Agent 接受项目经理派工。
项目资料根目录：<实际绝对路径>。
请阅读 <岗位 agent.md 的实际绝对路径>，以及其中要求的规则和资料，按该岗位配置完成只读初始化。
材料来源：<实际提交或当前工作区资料；如有副本差异，说明情况>。
本次只初始化，不执行开发、测试、审查，不修改文件，不创建子 Agent。
请回复岗位名称、正式任务 ID、实际工作目录、读取的配置与规则、职责及读写边界、资料缺失或冲突，并明确“等待派工”。
~~~

## 4. 等待并核实接手

- 使用 wait_threads 等待初始化完成；需要核对元数据或结果时使用 read_thread，不以创建工具返回成功替代接手完成。
- 核对回执与创建结果的正式 ID、项目、工作目录和岗位是否一致；接收方可读取 CODEX_THREAD_ID 辅助核实，不能只凭环境值确认身份。
- 核对要求的资料是否读全、职责与边界是否正确、是否明确等待派工。角色未获修改业务代码授权时不能因初始化自行开工。
- 回执不完整时，先在登记追加补充指令，再向同一任务 send_message_to_thread 补齐，不重新创建实例。
- 已有同一版本的明确确认直接沿用，不重复请求用户确认岗位；缺少配置、访问受限或工具失败时如实记录阻塞。

## 5. 登记并向用户汇报

docs/agent-roster.md 每个岗位保存：实际名称、实例类型、正式 ID 与 hostId、目录、配置来源、创建或复用结果、接手证据、当前状态。追加保留创建与补充记录；不写密钥或猜测的身份，不另建复杂状态文件。

全部明确岗位处理完后，用一张简短表报告“岗位／创建或复用／就绪、忙碌或阻塞”。持久化岗位的缺失配置或其他阻塞单独说明，不能把部分成功称为所有岗位已就绪。

创建新任务后按应用要求提供任务入口；后续派工复用登记的同一 ID。初始化不自动生成业务任务，初始化完成的岗位保持等待派工。

**完成条件：用户后端、管理后端、App 前端、管理后台前端、独立测试均有核实后的持久化实例及接手记录，或每个未完成岗位有明确阻塞原因；没有创建子 Agent。**
