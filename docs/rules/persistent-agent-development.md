# 第四步：执行任务

记录载体按[项目记录规则](task-records.md)执行：本步骤的循环产出写入 docs/plans/当前任务记录.md 下对应任务范围；完成后提纯至 docs/plans/<任务名>.md 并清理过程材料。文中的计划、报告和结论均指当前任务记录的对应章节或岗位返回内容，不要求逐步骤新建人工文件；必要原始证据按需单独保存并引用。

参考 superpowers 的 subagent-driven-development/SKILL.md，按本项目固定岗位方式调整：用户后端、管理后端、App 和管理后台前端分别由一个独立持久化 Agent 执行，不使用子 Agent，不按任务重新创建开发者。

本步骤保留原方法的任务上下文隔离、执行记录、实现与自检；逐任务审查、整改复审及最终整体审查统一按第五步规则执行。项目经理组织执行，不编写前后端代码。四个开发岗位分别遵循 happyAnyway-api/agent.md、happyAnyway-admin-api/agent.md、happyAnyway-app/agent.md 和 happyAnyway-admin/agent.md，本规则不替代岗位配置。

## 1. 固定执行岗位

| 岗位 | 负责工程 | 运行方式 |
|---|---|---|
| 后端开发 Agent | happyAnyway-api/ | 独立持久化任务，持续接收后端开发与整改任务 |
| App 开发 Agent | happyAnyway-app/ | 独立持久化任务，持续接收 App 开发与整改任务 |
| 管理后端开发 Agent | happyAnyway-admin-api/ | 独立持久化任务，持续接收管理 API 开发与整改任务 |
| 管理后台开发 Agent | happyAnyway-admin/ | 独立持久化任务，持续接收 Web 管理端开发与整改任务 |

查找并复用已确认的对应持久化任务；缺少岗位时按用户授权创建独立持久化任务，核实正式 ID、目录与配置接手结果后再开工。不得使用 spawn_agent 补位。开发 Agent 也不得自行创建子 Agent、招聘助手或另派审核者。

持久化保留的是岗位身份与交接记录，不代表聊天记忆可靠。每次接新任务都重新读取对应任务、版本与约束，不依赖上一任务的假设。

## 2. 核对执行条件与恢复位置

- 第二步计划及其确认方案可访问，第三步隔离工作区和基线检查已完成。
- 每项交付使用一份统一任务记录，保存分工、岗位 ID、分支、实际目录、版本、状态、证据位置和未解决问题；不再把计划和进度拆成两份文件。
- 接手或上下文恢复后，先核对执行记录与实际 Git 状态，继续未完成任务或整改轮次，不重复下发已完成工作，不混用其他计划的记录。
- 开工前对照规格检查任务间共享文件、接口供需及任务内部步骤是否一致，将发现写入记录。影响已确认范围或取舍的问题返回第一步，其余计划缺陷修正后同步受影响岗位。

## 3. 按任务交付必要上下文

每次只向对应岗位下发当前任务的完整要求及必要的共同约束：

1. 任务在项目中的作用、计划中的任务位置和已确认方案。
2. 本任务准确的目标、文件范围、接口、执行步骤和验收条件；引用共同约束时确保接收方可访问。
3. 前置成果及其版本、已经确认的接口决定和与本任务相关的遗留问题。
4. 实际执行目录、分支、任务开始前的基线提交，以及未提交内容的来源。
5. 报告位置与回复要求。

资料较长时给出具体文件和章节，不把整个会话历史反复粘贴给执行者。任务要求只有一个权威来源，消息摘要不得改写接口字段、数值或验收标准。提问缺少上下文时先补足，再要求执行。

每个岗位同一时间执行一项任务，其余排队；同类小改动可合并成一个有共同验收条件的批次。两端只在接口已明确、依赖满足且修改范围不冲突时并行；共享文件串行处理。

## 4. 实现、自检与报告

开发交付必须包含由开发 Agent 编写的[开发说明](task-records.md#开发说明)：简述实现内容，并用“使用页面或功能—变更文件—用途或变化”说明对应关系。由开发 Agent 保存到所属工程 docs/development/，按页面或功能持续维护并更新索引；任务记录只链接，缺少说明时交原开发岗位补齐。

结构变化须同步维护所属工程路书，报告列出更新位置和核对依据；无结构影响时简述无须更新的理由。按[路书维护规则](project-roadmap.md)执行。

开发岗位在授权范围内实现、运行相关测试并自检，将结果返回项目经理汇入当前任务记录，不另建人工任务报告。项目经理继续跟踪已授权任务，不在每项任务之间重复询问是否继续。

报告至少包含修改范围、成果版本或基线差异、验证命令与结果、未验证项和剩余问题。回复项目经理时提供状态及上述结果，由项目经理汇入指定任务章节；已有独立证据提供引用位置：

| 状态 | 项目经理处理 |
|---|---|
| DONE | 核对成果与自检证据，准备任务审核 |
| DONE_WITH_CONCERNS | 先处理正确性、范围或依赖疑虑；其他观察记录后交审核 |
| NEEDS_CONTEXT | 补充缺失信息，继续交同一岗位执行 |
| BLOCKED | 识别环境、任务范围或方案问题，改变阻塞条件后再继续 |

阻塞时不能原样反复重试，也不能由项目经理接手代码。需要修改模型或更换岗位时先取得对应授权，不按重试次数自动创建新 Agent。

## 5. 交付并进入审查

开发完成并提供自检证据后，项目经理核对材料，按[第五步：审查](code-review.md)组织独立审查。报告 DONE 只表示开发完成，不表示审查、测试或用户验收通过。

每个可独立验证的任务交审后，依赖其结果的任务按审查结论放行；不受影响的已授权任务可以继续。第五步要求整改时，由原持久化开发 Agent 返回本步骤修复、自检并更新报告，再交复审。

记录作为后续审查、测试和验收依据保留，不自动删除计划、报告或 worktree。提交、合并、推送、发布与清理按用户授权执行。

**完成条件：本任务实现和自检有证据，交付版本、变更范围、报告和剩余问题清楚，可交由第五步独立审查。**
