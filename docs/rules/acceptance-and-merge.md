# 第七步：用户验收后合并分支

记录载体按[项目记录规则](task-records.md)执行：本步骤的循环产出写入 docs/plans/当前任务记录.md 下对应任务范围；完成后提纯至 docs/plans/<任务名>.md 并清理过程材料。文中的计划、报告和结论均指当前任务记录的对应章节或岗位返回内容，不要求逐步骤新建人工文件；必要原始证据按需单独保存并引用。

合并后按[路书维护规则](project-roadmap.md)核对总路书和工程路书与最终目录、入口及状态一致，保留尚未落地和未验证项的标记。

参考 superpowers 的 verification-before-completion/SKILL.md 和 finishing-a-development-branch/SKILL.md，按本项目固定岗位和用户已确定的“验收通过后合并”流程调整。

项目经理核对证据、组织用户验收并执行获准的 Git 合并操作，不修改业务代码。顺序为：核验交付 → 用户验收 → 本地合并 → 验证合并结果 → 交接归档。

## 1. 核验交付证据

- 对照已确认需求和计划，逐项核对实际成果、审查结论、独立测试与缺陷复测结果；不能只凭 Agent 回复 DONE 判断完成。
- 每项成功声明必须有与当前交付版本对应的实际验证证据：明确验证命令或操作，执行检查，读取完整结果与退出码，再给结论。
- 核对两端交付提交、未提交修改和报告版本。代码、配置、依赖或目标基线变化后，安排对应岗位重新执行受影响验证，不能用旧结果证明新版本通过。
- 构建、lint、功能测试、数据库和真机验证分别记录；某一项通过不替代其他项。没有环境、未执行或证据不足的项目如实标明。
- 存在失败、未关闭阻塞缺陷或关键验收项未验证时，先报告并交原岗位处理，不声称具备全部验收条件。用户可以审阅当前成果，但不得把已知缺口包装成完成。

测试方法和复测由独立测试 Agent 按第六步规则执行。项目经理核对实际代码版本、产物与报告；缺少最新验证时安排补齐，不代替测试岗位给出独立通过结论。

## 2. 确定验收版本与合并目标

验收前记录：需求依据、两端源分支及完整提交、目标分支及其当前提交、相关 worktree 路径、分支或 detached HEAD 状态，以及未提交文件。

目标分支以本次计划或用户已有确认作为依据，不能猜测一定是 main/master；无法确定时先向用户澄清。未提交成果必须先按授权形成可核对的交付提交，不能验收一个工作区却合并另一组内容。

多个开发分支属于同一交付时，明确合并顺序及组合后的验收版本；必要时由开发在集成分支准备组合成果，完成审查测试后再交验收。不能用两个单独通过的分支，推断组合也通过。

## 3. 提交用户验收

提供一份可直接核对的验收摘要：

- 交付功能、演示或操作入口、逐项验收结果。
- 两端交付版本及本次范围。
- 审查、独立测试和复测证据的位置及结论。
- 未完成项、未验证项和剩余风险。
- 验收通过后准备合并的源分支、确切提交与目标分支；默认只做本地合并。

用户明确验收通过后才执行合并。用户要求修改时交原岗位整改，并按影响复审、复测和重新验收。沉默、演示结束、开发自检或测试通过均不能替代用户验收。

本项目已选择“验收后合并”的流程：源版本和目标分支明确且没有变化时，用户验收通过后继续执行，不再重复询问是否合并。用户选择暂留分支、改走 PR 或附带条件时，遵从具体指示；附带条件是否允许立即合并必须明确。

## 4. 安全执行本地合并

1. 重新读取 Git 状态及 worktree 列表，核实源提交仍是已验收版本、目标分支正确、没有正在写入的 Agent 或会被覆盖的修改。
2. 已验收源分支又有新提交时不把新内容一并带入；目标分支发生变化时，先验证待合并组合，影响已确认行为或范围的变化须重新验收。
3. 在目标分支实际所属工作区进行合并，不能在其他岗位正在使用的目录擅自切换分支；目标已被其他 worktree 占用时使用相应目录并协调停止写入。
4. 若平台提供适用于该任务的原生合并能力，按其操作；否则使用 Git 合并已核实的源提交。记录合并前的目标提交，合并后核实目标包含全部已验收提交，记录新的目标提交。
5. 不机械执行 git pull 引入未经验证的远端变更；需要同步时先核对远端差异及对验收的影响。
6. 出现冲突时停止放行，保留冲突现场与记录，交原开发岗位处理。项目经理不修改冲突中的业务代码，不使用强制覆盖或随意选择 ours/theirs。解决后按影响复审、复测；改变验收内容时重新确认。

创建中的临时任务标识不能充当分支依据。外部管理的 detached HEAD 先通过平台能力或获准的分支安排固定交付提交，不擅自切换或清理其工作区。

## 5. 验证合并后的结果

对实际合并提交重新运行本次交付所需的检查，由对应岗位提供结果：

- 后端：在 happyAnyway-api/ 执行 mvn verify，以及交付功能要求的相关验证。
- App：在 happyAnyway-app/ 执行 npm run lint、npm run typecheck、npm test 及 README 中的双平台构建检查；原生构建、独立安装和设备联调分别验证。
- 跨端交付：检查两端接口、配置和依赖组合，按影响执行独立回归；真实数据库或设备结果不能由构建通过推断。

读取实际输出、退出码、测试数量与失败项，并记录验证对应的合并提交。失败时报告“本地已合并，但验证未通过”，保留分支与工作区，安排排查；不推送、不发布、不清理，不声称交付完成，也不擅自 reset 掩盖失败。

## 6. 报告结果并进入归档

报告用户验收依据、已合并源提交、目标分支与合并后提交、实际验证结果、遗留问题，以及是否推送。全部所需条件满足后进入第八步“Harness 记录归档”。

本步骤默认完成本地合并。推送、PR、发布和删除分支或 worktree 按用户另外授权执行，已有明确授权可沿用，不扩大范围。

清理时核对第三步保存的工作区来源、任务归属和实际文件：平台管理的工作区使用平台能力处理，不能仅凭目录名认定可删除。只清理本次明确授权的对象，从工作区外操作；有未提交或未跟踪文件时先交代内容和处理选择，不使用强制删除绕过保护。用户没有要求丢弃成果时不执行丢弃操作。

**完成条件：用户已验收明确版本，内容已合入正确目标分支，合并后验证有实际结果，合并状态与遗留风险已报告。**
