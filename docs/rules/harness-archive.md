# 第八步：Harness 记录归档

采用用户确认的方案 A：按交付归档，规则按需更新。项目经理整理交付总结，各岗位补充其成果与证据；通过索引保留上下文，不重复复制整套材料。

## 1. 确认归档时点和状态

正常交付在第七步用户验收、分支合并及合并后验证完成后归档。暂停或取消的工作也可以归档，须明确实际状态、停止原因、已完成部分和恢复条件，不能记为验收通过。

## 2. 每次交付保存一份总结

按需创建 docs/archive/YYYY-MM-DD-交付主题.md；同日同主题用可区分的名称，不覆盖其他交付。不提前创建空归档模板。

总结包含：

| 内容 | 记录要求 |
|---|---|
| 交付概况 | 目标、实际完成范围、日期和最终状态 |
| 版本与验收 | 用户验收依据、两端交付版本、目标分支与合并提交；不适用或未完成时如实说明 |
| 证据索引 | 链接已有设计、计划、执行报告、审查、测试及合并后验证记录，并概括结论 |
| 遗留事项 | 问题、影响、责任岗位、后续处理安排；未知或待确认的安排明确标注 |
| 经验总结 | 实际遇到的问题、原因、有效做法及适用条件 |
| 规则建议 | 有依据的改进建议与确认状态；没有需要修改的规则时写明无 |
| 后续交接 | 下一步事项、接收岗位和继续工作所需的入口 |

原材料保持原位。优先使用可长期访问的仓库相对链接，并写明证据对应的版本；同一资料有多个修订时，定位本次实际使用的版本，不能只指向不断变化的最新文件。

依赖即将清理的 worktree、临时日志或本机文件时，先核对必要证据能否长期访问，按已有授权安排保留，并更新入口。不得用将失效的路径宣称归档完成，也不为了完整而复制无关日志、密钥或真实业务数据。

## 3. 保留问题和可复用经验

- 未解决问题、未验证项和已接受风险继续保留；归档不代表它们自动关闭。
- 区分事实、原因判断和改进建议，不把尚未证实的推测写成结论。
- 一次性问题记录在本次总结中；跨任务仍有价值的经验才考虑形成规则。
- 以接手者能找到成果、理解状态和继续工作为准，不复述全部聊天或重复已有报告。

## 4. 规则按需更新

只针对实际暴露的问题提出修改，说明原问题与证据、拟修改内容、预期作用和影响的岗位或步骤。可以修正、合并或删除失效规则，不以增加条款作为复盘成果。

项目经理将具体改动交用户确认；确认后更新对应规则及必要引用，记录确认依据，并通知受影响岗位。用户已经明确批准的具体改动直接执行，不重复索要同一确认；建议未获确认前不能作为新要求派发。

## 5. 完成交接

核对归档入口可访问、证据与结论一致、遗留事项有明确状态后，向用户提供总结位置与下一步事项。已有进度记录时更新其交付状态并链接归档，不另建重复台账。

归档不自动提交、推送、删除分支、移除 worktree 或清除原始证据；这些操作依各自授权执行。

**完成条件：一份总结能定位本次交付与证据，遗留事项和后续安排明确，规则修改有实际依据且经过用户确认。**
