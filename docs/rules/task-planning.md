# 第二步：任务拆解与派工

由项目经理执行。依据第一步已确认的方案，编写接收 Agent 无需依赖聊天记忆即可执行的计划，再下发给对应岗位。

参考 superpowers 的 writing-plans/SKILL_CN.md，按本项目的岗位职责、技术栈、现有工程和用户已确认的协作方式调整。保留可执行计划、明确文件与接口、验证步骤、规格覆盖检查及执行交接等核心要求；调整应有具体项目依据，不以缩短文档或减少步骤为目标。项目经理负责计划，不编写前后端实现代码或测试代码。

## 1. 核对输入与范围

- 读取已确认的设计文档或聊天方案，确认目标、范围、约束及验收条件；关键业务问题未确认时，返回第一步澄清。
- 核对当前代码及相关文件。记录需求版本或确认依据，以及代码基线；使用 Git 时记录实际提交，未提交修改另说明范围与来源，不能假定接收方已经看到。
- 多个可独立交付的子系统分别形成计划，说明依赖和先后顺序。只安排已确认范围，不附加无关重构或预留功能。

## 2. 先列文件与接口，再划分任务

先确定涉及哪些文件、各自负责什么，以及前后端或相邻任务之间如何衔接；遵循项目现有结构。

每项任务以一个可独立验证的成果为边界。设置、配置、实现、测试和必要说明归入它们所服务的成果，不把每个命令或文件都拆成独立任务。

需要共同修改同一文件，或依赖尚未确定的接口时，明确执行先后；只有依赖满足且修改范围不冲突的任务才能并行。

## 3. 写成可执行的计划

计划按需保存到 docs/plans/YYYY-MM-DD-主题.md。简单改动只写一项完整任务，不为了格式扩充内容或另建重复文档。

计划开头写清：

- **目标与范围**：要交付什么、本次不做什么。
- **依据**：已确认方案的位置、版本或确认依据，以及实际代码基线。
- **总体做法与技术栈**：简述实现方向、沿用的技术和必要限制。
- **共同约束**：所有任务都要遵守的准确约定，例如接口字段、版本要求、文案或平台限制。

每项任务包含：

| 内容 | 写清什么 |
|---|---|
| 任务名称与接收岗位 | 一个明确成果，由哪个岗位负责 |
| 输入与依赖 | 要读取的资料、前置成果、何时具备开工条件 |
| 文件范围 | 新建、修改、测试文件的具体路径及用途；计划中的新路径须明确标注 |
| 接口约定 | 使用和提供的接口、参数、返回值、错误情况；无跨任务接口时说明不涉及 |
| 执行步骤 | 用复选框列出单一、可检查的操作，顺序清楚，交给执行岗位实现 |
| 验证方式 | 在哪个目录执行哪些命令、检查哪些行为、预期结果和所需环境 |
| 交付物与验收条件 | 成果位置、可观察的通过标准、需要反馈的验证结果和限制 |
| 优先级与安排 | 前后顺序、可并行项；估算有依据才给出，未知则说明 |

涉及业务行为时，步骤应说明需要验证的输入、预期输出、异常和边界场景。适用时安排开发先编写能复现问题的失败测试，再实现并运行验证；具体代码由开发岗位编写。文档等低影响改动使用与改动相称的检查方式。

计划不使用“添加适当校验”“处理边界情况”等无法验收的表述。例如应明确“缺少必填字段时返回约定的错误码且不写入数据库”，而不是只写“完善错误处理”。

## 4. 下发前自审

项目经理直接对照方案检查，不为计划自审另建 Agent：

1. 每条需求和验收条件都能对应到具体任务，没有漏项或额外范围。
2. 每项任务都有接收岗位、文件范围、输入、交付物与验证方式；不存在阻塞执行的占位内容。
3. 上下游接口名称、字段、类型及错误约定一致；引用的资料和现有文件可访问。
4. 依赖顺序可执行，并行任务不会争抢同一文件；估算与验证结果没有伪造。

计划缺陷直接修正。发现必须改变已确认方案的范围、接口或关键取舍时，返回第一步确认受影响部分。

## 5. 保存并下发

- 保存计划后，向用户简述拆分结果和执行顺序；已有明确授权且方案未变时，不重复要求确认。
- 开发任务分别交给后端、微信、网页前端三个固定持久化 Agent，查询并复用已有岗位；缺岗时按用户授权创建独立持久化任务，不使用子 Agent。忙碌时排队，身份或配置未核实时先补齐。审查由项目经理在第五步按需创建独立审查子 Agent；测试交给已初始化的独立持久化测试 Agent。
- 向接收 Agent 提供所属任务、计划与方案位置、版本依据、允许修改范围、依赖、交付要求和验收条件；共同约束随任务一同提供。
- 在计划中简记实际接收 Agent、下发结果和当前状态。未确认接收时不写成已开工；前置未满足的任务只排队，不下发开工要求。
- 下发时注明“待第三步隔离环境就绪”，提供计划与基线，允许接收方只读核对；进入第三步“创建隔离分支”，核实实际工作区及基线检查后才允许修改代码。不把原文的“每项任务新建子代理”或“项目经理内联实现”作为默认执行方式。

本规则不引入额外技能依赖，不要求自动创建工作树或提交 Git；提交、推送和发布依用户授权执行。

**完成条件：任务覆盖已确认方案，职责与依赖明确，接收 Agent 能找到依据、知道交付什么以及如何验证，实际下发结果可查。**
