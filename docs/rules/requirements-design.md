# 第一步：明确目标、范围与需求方案

记录载体按[项目记录规则](task-records.md)执行：本步骤的循环产出写入 docs/plans/当前任务记录.md 下对应任务范围；完成后提纯至 docs/plans/<任务名>.md 并清理过程材料。文中的计划、报告和结论均指当前任务记录的对应章节或岗位返回内容，不要求逐步骤新建人工文件；必要原始证据按需单独保存并引用。

由项目经理执行，不设置独立产品 Agent。目标是通过与用户对话，把需求变成可以拆分和验收的方案；项目经理不编写前后端代码。

参考 superpowers 的 brainstorming/SKILL_CN.md，按本项目的岗位职责、技术栈、现有工程和用户已确认的协作方式调整。保留需求澄清、方案权衡、设计确认和规格自审等核心要求；调整应有具体项目依据，不以缩短文档或减少步骤为目标。

先按 [AGENTS.md 的流程适用范围](../../AGENTS.md#流程适用范围)判断是否采用轻量处理。不更改代码或范围明确的小任务，不强制逐项设计确认、拆解和派工；明确请求直接执行，有影响结果的歧义才澄清。下文适用于需要完整方案设计的任务。

## 1. 先理解上下文，再选择路径

先阅读与请求有关的代码、文档和已有决定，有 Git 时查看相关变更。了解现有能力，不重复询问资料已经说明或用户已经确认的事项。

用一句话说明本次采用哪条路径及原因，用户可以调整：

| 路径 | 适用情况 | 本步产出 |
|---|---|---|
| 可行性探查 | 主要问题是“能不能做”，需要先验证未知条件 | 探查问题、范围及成功标准；探查完成后形成结论和建议 |
| 局部改动 | 仓库已有可读的相关流程，改动范围明确 | 聊天中的简短方案，说明改动范围、预期行为和验证方式 |
| 新功能或架构调整 | 新项目、新子系统、影响其他模块的接口或结构变化 | 方案比较及一份简明设计文档 |

不因熟悉应用类型就将新项目视为局部改动。遇到影响范围的未知项，先澄清；发现复杂性超出原路径时，说明变化并调整方案。涉及多个独立子系统时，先与用户确定分期和先后顺序。

## 2. 逐个澄清关键问题

- 每次只问一个关键问题，能给出清晰选项时优先用选项，允许用户补充。
- 围绕目标用户、使用场景、做与不做、约束、优先级及成功标准展开；已有答案不重复问。
- 区分已确认事实、建议和待确认项；影响业务取舍的未知项交由用户决定，不自行猜定。

## 3. 提出与规模相称的方案

- 可行性探查：用两三句话说明要验证什么、如何验证、做到什么程度即可，避免把探查直接扩展成正式功能。
- 局部改动：简述做法、涉及位置、预期行为与验证方式；存在关键取舍时再对比备选方案，不为凑数量增加方案。
- 新功能或架构调整：提出 2—3 个可行方案，说明优缺点、实现成本、风险及推荐理由；估算依据不足时如实说明。
- 只设计当前需要的内容，不加入无关重构或预留功能。开发评估可行性，测试评估可验证性；尚未获得反馈时明确标注。

## 4. 呈现设计并确认

按任务需要说明目标与范围、用户流程、模块或页面、接口与数据、异常处理和验收条件。简单改动用几句话；复杂设计分节讨论。只有图示或原型能帮助理解时才使用可视化。

将具体方案交给用户明确确认后，才能进入下一步。用户已明确确认且未发生变化的内容直接沿用；推荐、沉默和等待超时不能代替确认。方案改变了范围、接口或关键取舍时，只重新确认受影响部分。

这一阶段可以阅读资料、讨论和编写设计文档，不下发未经确认的开发实施任务。项目经理始终不接管前后端代码实现。

## 5. 保存结果，交给任务拆解与派工

- 可行性探查：用户确认探查范围后进入任务拆解与派工，由对应岗位执行；需要代码时由开发岗位承担。结论必须区分已验证、未验证和限制。探查产物标明是否为一次性试验，转成正式功能前重新确认方案。
- 局部改动：保留聊天中的方案与用户确认，下一步创建任务时带上这些依据，无需另建重复设计文档。
- 新功能或架构调整：在任务记录中写清方案、取舍、验收条件与确认状态；仅长期复用的重要设计单独保存到 docs/designs/YYYY-MM-DD-主题.md 并引用。先自查遗漏、矛盾和模糊项，再请用户审阅实际文档；用户确认最终内容后进入任务拆解与派工。

未解决且影响实施的关键问题不得写成已确认。设计文档按需创建，不生成空模板；本规则不要求自动提交 Git，也不依赖其他技能。

**完成条件：目标、范围、方案、验收方式和用户确认依据清楚，下一步可以据此拆分并下发任务。**
