# 第三步：创建隔离分支与工作区

由项目经理组织，为第二步已下发的开发任务准备隔离分支和 Git worktree。分支隔离提交历史，worktree 提供独立工作目录；只切换分支不等于目录隔离。

参考 superpowers 的 using-git-worktrees/SKILL_CN.md，按本项目双工程结构、岗位边界和用户授权调整。保留先检测、优先原生工具、验证目录与基线的顺序。

## 1. 核对任务和 Git 前置条件

- 确认任务、接收 Agent、依赖、计划位置和第二步记录的代码基线；任务已接收不代表可以开始修改代码。
- 检查实际执行目录是否属于正确的 Git 仓库，并保留已有修改。未初始化 Git 或没有可用提交时，先说明缺失条件并按用户授权建立基线，不声称已具备隔离条件。
- 未提交的代码、需求和计划不会自动出现在新 worktree 中。明确采用的提交或材料交接方式，不擅自提交、丢弃或暂存用户修改。
- 用户已指定隔离方式或目录时沿用。当前流程要求开发前完成隔离，无须对同一隔离意图反复确认；改变执行方式时说明原因。

## 2. 先检测已有隔离

在接收 Agent 实际执行目录运行：

~~~powershell
git rev-parse --show-toplevel
git rev-parse --absolute-git-dir
git rev-parse --path-format=absolute --git-common-dir
git rev-parse --show-superproject-working-tree
git branch --show-current
git worktree list --porcelain
git status --short
~~~

将 Git 目录和公共 Git 目录解析成绝对路径后比较，并结合 worktree 列表核实：

- 已在链接 worktree，且属于本任务：复用，不再嵌套创建。
- 已有其他任务占用的 worktree：不挪用，按本任务单独安排。
- 子模块检查返回路径：不能仅凭目录差异认定已有任务隔离，先确认所属仓库。
- 分支名称为空：记录为 detached HEAD；不要擅自切换外部管理状态，需要提交成果时核实分支安排。

记录实际路径、分支或 HEAD、基线提交和干净状态。

## 3. 优先使用平台原生 worktree 能力

优先使用当前平台提供且适用于目标任务的 worktree 创建或迁移工具，按工具规则选择项目与基线，等待操作完成，再核实返回的目录、分支和正式任务 ID。

已有持久化岗位应优先复用，不能为了创建 worktree 重复创建同岗位 Agent；需要迁移已有任务时，先核实其当前工作已停止。工具只支持其他任务时，不把它当作移动当前任务的能力。

只有平台没有适用的原生能力时，才进入下一步手动创建。原生工具失败应先核实结果，避免重复创建或形成平台无法管理的目录。

## 4. 无适用原生能力时，用 Git 创建

目录按顺序选择：用户指定位置 → 已有 .worktrees/ → 已有 worktrees/ → 项目根目录下 .worktrees/。

项目内目录必须先验证已被 Git 忽略，例如：

~~~powershell
git check-ignore -v .worktrees/
~~~

未忽略时，在授权范围内补充根 .gitignore 并重新验证；需要提交该改动时遵循用户提交授权，不自动提交。使用其他目录时检查实际选中的路径，不以无关目录通过检查代替。

创建前核实目标绝对路径、分支与 worktree 均无冲突，不覆盖现有目录。分支默认使用 codex/ 前缀，用户明确指定其他名称时遵从。确认实际值后执行：

~~~powershell
git worktree add -b <任务分支> <新工作区绝对路径> <已确认的基线提交>
~~~

命令中的占位内容必须替换为已核实的实际值。创建后重新检查目录、分支、提交和 Git 状态；后续命令在该目录中运行。

权限阻止创建时先使用允许的权限申请方式；仍无法完成则报告阻塞。不能将就地开发标为隔离成功；只有用户明确同意改变方式后才就地执行。

## 5. 在隔离工作区验证项目基线

按任务涉及范围安装依赖并验证。后端任务检查后端，小程序任务检查小程序，跨端任务检查两端；共同构建配置变化按影响范围扩大检查。

| 工程目录 | 准备与检查 | 通过标准 |
|---|---|---|
| happyAnyway-api/ | Java 21 与 Maven 可用，执行 mvn verify | 构建成功，相关基础测试通过 |
| happyAnyway-wechat/ | Node.js 22+，执行 npm ci，再执行 npm run lint、npm run typecheck、npm run build | 各命令成功，类型检查和编译通过 |

命令依据实际工程配置核对，不假定根目录存在 package.json。不复制旧目录的 node_modules 或 target 作为验证依据；构建产物与本机配置不作为需求交接材料。

测试失败或依赖、环境缺失时，报告具体命令、结果和影响，并由用户决定先排查还是带已知问题继续。未执行的检查明确标为未验证，不记为通过。基础构建不代表 MySQL、开发者工具或真机联调已通过。

## 6. 交接给执行岗位

向接收 Agent 提供任务、计划和方案位置，以及工作区绝对路径、分支或 HEAD 状态、基线提交、验证结果和遗留问题。在第二步计划中更新实际执行目录与任务状态。

隔离与基线条件满足后，进入第四步“执行任务”，由后端、微信两个固定持久化 Agent 开始实现和自检。项目经理跟踪结果，不编写前后端代码，不创建开发子 Agent；第五步的独立审查子 Agent 按审查规则创建。

**完成条件：接收 Agent 的执行目录与版本明确，隔离方式已核实，基线检查有实际结果，开工条件和未验证项已说明。**
