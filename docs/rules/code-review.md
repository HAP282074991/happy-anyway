# 第五步：审查

参考 superpowers 的 requesting-code-review/SKILL.md 与 receiving-code-review/SKILL.md，按本项目固定持久化岗位、独立审查和用户决策边界调整。

项目经理组织审查与问题流转；审查者独立核对要求和代码；原后端或微信开发 Agent 核实意见并整改。审查由项目经理按需创建独立子 Agent 执行，本文件即其工作规则，无需另建持久化审查岗位。审查子 Agent 不参与被审查内容的实现，也不由实现者的自检代替独立审查。

## 1. 确定审查时点

- 每个可独立验证的任务完成实现与自检后，按本规则审查；影响后续任务的阻塞问题解决后再放行相关依赖。
- 主要功能完成后，对整体交付审查一次，检查跨任务和跨端接口及规格覆盖，不能只拼接各任务的通过结论。
- 合并前核对审查是否仍对应当前交付版本；后续修改按影响补充审查，不能用旧结论覆盖新代码。
- 遇到复杂缺陷、重构或技术阻塞时，可提前请求针对性审查，明确问题与范围。

第四步与第五步可按任务形成“实现、自检 → 审查 → 整改、复审”的循环；所有任务完成后进行整体审查。审查不代替第六步的独立功能与联调测试。

## 2. 准备审查材料

项目经理提交以下材料，提供可访问的文件与版本，不粘贴整个会话历史：

1. 本次实现的简述、所属任务及范围。
2. 已确认的需求或方案、计划中的任务要求和准确的共同约束。
3. 实现与自检报告，包括命令、结果、环境限制及未验证项。
4. 审查基线 BASE、交付版本 HEAD、完整变更和已知问题。

BASE 使用任务开始前记录的提交；多次提交的任务不能直接以 HEAD~1 代替。已提交变更可用 git log、git diff --stat 和 git diff 生成审查材料。存在未提交修改时，补齐相对基线的暂存、未暂存差异及新增文件内容，不把未提交成果描述为提交版本。

审查材料按任务和轮次保存，避免覆盖旧结论对应的版本。两端位于不同分支时分别提供基线与交付版本，并说明接口关系。

## 3. 独立审查并形成结论

### 创建与交接审查子 Agent

1. 项目经理在当前计划执行记录中保存审查范围、轮次、准确版本和完整派工要求，再使用 spawn_agent 创建审查子 Agent。审查属于已授权交付流程时，无须逐次请求用户确认；不在初始化持久化岗位时提前创建。
2. 创建消息明确：审查角色、本规则的绝对路径、实际代码目录、需求与计划位置、两端适用的结构与开发规则、BASE 与 HEAD 或未提交变更范围、自检证据、报告位置。要求先读材料，再独立判断，不预设通过结论。
3. 明确权限：源码及 Git 状态只读，仅可写指定审查报告；不继承项目经理的管理权限，不修改业务实现、不转派、不创建下级 Agent。子 Agent 共享目录，创建本身不代表已有工作区隔离；核对路径，避免影响开发中的文件。需要运行会产生文件的验证时，另行明确隔离目录和允许产物范围。
4. 保存实际子 Agent 标识及派工结果，等待并读取完整结论。创建成功或进度消息不等于审查完成；失败或材料不足时记录阻塞，不能由项目经理代签通过。
5. 同一任务整改复审优先交原审查子 Agent。原实例不可用时，可创建新的独立审查子 Agent，提供历次意见、版本和整改证据并记录接替关系。审查结束保存报告，不登记为持久化岗位。

### 审查内容与结论

审查者实际读取要求、相关代码和验证证据，检查：

- **规格符合性**：需求是否完整实现，是否擅自扩大范围，偏离方案是否有依据。
- **代码质量**：职责划分、异常处理、类型安全、重复代码、边界场景及与现有结构的一致性。
- **技术与安全**：接口兼容性、权限和数据风险；涉及数据库时检查迁移与回退影响，涉及小程序时检查平台约束。
- **验证充分性**：测试是否验证实际行为，关键异常和跨端接口是否有覆盖，未验证项是否如实说明。

对被审查代码目录只读，不修改工作树、暂存区、HEAD 或分支，不直接代开发修复。需要检查其他版本时使用适合的独立只读材料或隔离目录，不切换开发者当前目录的版本。报告写入预先约定的位置。

每条问题包含文件位置、具体问题、影响、依据和必要的复现或修复建议；按实际影响分类：

| 等级 | 处理方式 |
|---|---|
| Critical：严重缺陷、安全或数据风险 | 立即交回修复，阻止受影响成果放行 |
| Important：需求缺失、逻辑问题、关键验证缺口等 | 修复并复审后才能放行相关成果 |
| Minor：不阻塞交付的改进 | 记录影响与处理安排，纳入整体审查，不静默丢弃 |

报告分别给出“规格符合性”和“代码质量”结论，以及通过、需整改或无法验证的总体判断。未读代码不能凭印象给结论；无法从差异确认的要求须补充上下文，不直接记为通过。项目经理不能预先指示忽略某项问题或降低其严重程度。

## 4. 接收意见时，先理解和验证

开发 Agent 收到意见后按顺序执行：完整阅读 → 理解要求 → 核对实际代码和使用场景 → 评估技术影响 → 回复依据 → 逐项整改。

- 意见不清楚时先提出具体问题，厘清整组意见之间的关系再开始这组整改，不按猜测修改。
- 核实建议是否适用于当前 Java、Spring Boot、MyBatis 或微信小程序环境，是否破坏已有功能、接口兼容性或用户已确认的设计。
- 建议增加能力时，核对实际调用和已确认需求；没有需求依据的新增功能不能因“更专业”就加入。
- 无法验证时说明缺少的材料或环境；不把审查者身份当作技术正确性的证明。
- 意见正确时说明将修复的问题，完成后提供修改位置与验证结果。意见有误时给出代码、测试或运行证据并请求澄清，不盲目赞同，也不无依据反驳。
- 与已确认方案冲突、存在审查争议或涉及业务取舍时，项目经理记录双方依据交用户决定；争议项及依赖其结论的放行保持暂停。

## 5. 整改、验证与复审

1. 项目经理将经核实的意见交回原持久化开发 Agent，不自行编写代码，也不为每条意见创建新执行者。
2. 先处理阻塞、安全和功能错误，再处理其他修复；逐项验证受影响行为，相关问题可成组处理，但结果必须可追溯。
3. 开发报告每项处理结果、修复版本、覆盖测试、执行命令和输出；未解决项如实保留。
4. 审查者依据上一轮审查版本到本轮修复版本的差异复审，逐项判定已解决、未解决或需补充证据，并检查修复引入的新问题。
5. 修复范围外的观察另行记录，不无故扩大复审；修复后的新严重或重要问题仍须处理。

同一任务最多连续进行五轮整改复审；仍有问题时暂停相关任务和依赖放行，汇总尝试记录交用户决定。达到轮次上限不代表通过，不自动豁免缺陷或更换模型。

若核实后发现先前判断有误，直接更正结论并说明证据，不维护错误结论。未经明确确认的延期处理不能写成已接受风险。

## 6. 整体审查与交接

各任务审查后，对本次完整交付检查跨端契约、需求覆盖、版本一致性和累计遗留问题。整体问题按所属工程集中交原岗位整改并复审。

严重、重要问题和关键证据缺口关闭后，汇总交付版本、审查结论、整改与复审记录、剩余风险，进入第六步“交接独立测试”。后续变更使相关审查结论失效时补审。

记录保留在本计划的资料中。无需额外创建重复台账；审查通过不等于用户验收或合并、推送、发布授权。

**完成条件：要求与代码均已独立审查，意见经过技术核实，整改有复审证据，结论对应确切版本，未解决事项和放行状态明确。**
